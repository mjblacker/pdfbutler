# Desktop GUI frameworks and deployment for a lightweight Windows/Linux PDF viewer

## 1. Is Avalonia with F# a practical default, and which UI style minimizes maintenance?

### Takeaway

**Recommendation: start with F# on .NET 10 LTS and Avalonia, using a small plain-XAML shell with explicit view construction and simple view models.** FuncUI is a credible F#-first alternative, not an abandoned experiment; choose it if its typed DSL/state model materially improves the team's maintenance experience. NativeAOT should be an early feasibility experiment and a measured release option, not a prerequisite for the first prototype. These are project-specific judgments, based on the official F# templates, compiled-binding support, and AOT restrictions cited below.

Research checked **2026-11-03**. No application was implemented and no startup, memory, package-size, or compilation-time measurements were made. Framework performance statements below are documented architectural characteristics or explicitly labeled expectations—not measured results for this viewer.

#### Plain Avalonia XAML/MVVM with F#

- Official Avalonia templates explicitly include **F#** for app, MVVM app, cross-platform app, window, user-control, and templated-control projects. The README specifies `-lang F#`; F# does not require FuncUI to use Avalonia. [Official template repository](https://github.com/AvaloniaUI/Avalonia.Templates)
- The official F# window template inherits `Window` and explicitly calls `AvaloniaXamlLoader.Load(this)` from an initialization member. This is the actual supported template pattern, rather than assuming C# generated partial-class code can simply be copied into F#. The method name alone is not proof of runtime text-XAML parsing: use the Avalonia build/publish pipeline and verify the resulting AOT binary. [F# window template source](https://github.com/AvaloniaUI/Avalonia.Templates/blob/main/templates/fsharp/app-mvvm/Views/MainWindow.axaml.fs), [Avalonia AOT/XAML guidance](https://docs.avaloniaui.net/docs/deployment/native-aot)
- Avalonia 12 enables compiled bindings by default. Supplying `x:DataType` gives build-time errors for unresolved property paths; `ReflectionBinding` remains an explicit escape hatch. Thus “XAML is necessarily stringly typed and unsafe” is too broad: compiled binding paths have compile-time checks, although the whole UI is not equivalent to an F# domain model. [Compiled bindings](https://docs.avaloniaui.net/docs/data-binding/compiled-bindings)
- The template README exposes `--remove-view-locator` and specifically says the default view locator is not trimming-friendly. It also contains some stale/conflicting prose: an introductory sentence says the MVVM template uses ReactiveUI, while the options table lists CommunityToolkit as the default. Inspect the generated **F#** project rather than assuming the README's C#-oriented defaults or source-generation facilities apply identically. [Official templates](https://github.com/AvaloniaUI/Avalonia.Templates)
- Avalonia core is MIT-licensed. Retain notices and independently audit the PDF engine, native graphics dependencies, icons/fonts, and any commercial controls; the UI toolkit's license does not determine the whole application's license. [Avalonia license](https://github.com/AvaloniaUI/Avalonia/blob/master/licence.md)

#### FuncUI

- FuncUI describes itself as a thin layer over Avalonia consisting mainly of a virtual DOM, view DSL, and component model, with state management and examples for both components and Elmish. Its README lists four co-maintainers and a commercial-support provider. These are concrete maintenance signals, not a support SLA or a guarantee of future release cadence. [FuncUI README](https://github.com/fsprojects/Avalonia.FuncUI)
- FuncUI 2.0 follows Avalonia 12 breaking changes and moves DataGrid bindings into a separate community package. This demonstrates that even a thin wrapper must track upstream API changes; a PDF viewer without a data grid need not add that dependency. [FuncUI migration notes](https://github.com/fsprojects/Avalonia.FuncUI), [v2.0.0 release](https://github.com/fsprojects/Avalonia.FuncUI/releases/tag/v2.0.0)
- FuncUI's v1.5.2 release explicitly includes “get the control catalog working in NativeAOT builds.” This is positive evidence that real FuncUI code has been AOT-published, **not** proof that every FuncUI package, app, control, or current dependency combination is warning-free and AOT-safe. [v1.5.2 release notes](https://github.com/fsprojects/Avalonia.FuncUI/releases/tag/v1.5.2)

#### NativeAOT caveats for either F# UI style

- Avalonia documents NativeAOT deployment and recommends compiled bindings, build-time XAML, avoiding runtime dynamic XAML, compile-time/explicit dependency registration, and avoiding reflection-based service location. It warns that some third-party controls are incompatible and that dynamic control creation can need trimmer configuration. [Avalonia NativeAOT](https://docs.avaloniaui.net/docs/deployment/native-aot)
- .NET NativeAOT has no runtime JIT or runtime code generation, does not support arbitrary dynamic assembly loading or C++/CLI, requires trimming, and has diagnostic limitations. It still includes runtime support such as GC; “no preinstalled .NET runtime required” is accurate, whereas “no runtime exists” is not. [Microsoft NativeAOT overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
- `IsAotCompatible=true` enables analyzers and related properties; it is not a magic compatibility repair. Microsoft advises analyzing the application and dependency graph, and notes that some runtime-library warnings may not be actionable by an app author. [AOT compatibility analysis](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
- Avalonia's guide mentions rooting assemblies as a response to reflection issues. Rooting broad assemblies can preserve required metadata/code, but should not be presented as proof that dynamic-code requirements are fixed; NativeAOT still prohibits runtime code generation. [Avalonia reflection guidance](https://docs.avaloniaui.net/docs/deployment/native-aot), [Microsoft limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

### Inferences

- **Lowest-dependency starting point:** retain F# records/discriminated unions for application state and decisions; expose only a narrow UI-facing model for bindings/notifications. Use explicit views and commands rather than adopting a reflection-heavy locator/DI stack for one window. This recommendation follows the official F# template and AOT restrictions; it is not a claim that every MVVM toolkit is expensive. [F# templates](https://github.com/AvaloniaUI/Avalonia.Templates), [AOT guidance](https://docs.avaloniaui.net/docs/deployment/native-aot)
- **Plain XAML vs FuncUI:** XAML keeps the UI closer to Avalonia's main documentation and avoids a second UI abstraction dependency. FuncUI moves view composition and message/state modeling into F# and may improve local reasoning for an F#-focused maintainer. Its virtual-DOM/component layer introduces another update mechanism and compatibility surface, but no evidence collected establishes a meaningful startup penalty for this tiny shell. Choose on maintenance ergonomics, then measure. [Templates](https://github.com/AvaloniaUI/Avalonia.Templates), [FuncUI architecture](https://github.com/fsprojects/Avalonia.FuncUI)
- **Typed state does not remove native lifetime obligations:** whichever UI style wins, isolate native PDF handles, bitmap ownership, cancellation, and UI-thread dispatch behind a small explicit boundary. F# type safety should help the domain model without pretending external pointers are automatically safe. [P/Invoke model](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke)
- **Avoid blanket F# AOT claims:** ordinary F# application code and FuncUI have a plausible AOT route, but reflection-based serialization, dynamically discovered types, quotation-to-runtime-code utilities, or third-party dependencies must be evaluated individually. Do not classify all F# as incompatible, or all F# as automatically compatible, based on language choice alone. [NativeAOT restrictions](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [FuncUI AOT example history](https://github.com/fsprojects/Avalonia.FuncUI/releases/tag/v1.5.2)
- **Cold-start hypothesis, not measured fact:** an Avalonia shell without a browser engine and without eager heavyweight services is a reasonable candidate for the user's startup goal. AOT may reduce managed startup work, but it cannot eliminate native graphics initialization, font discovery, document parsing, or first-page rendering. No time-to-first-page guarantee follows from the toolkit name. [Avalonia platform architecture](https://docs.avaloniaui.net/docs/supported-platforms), [Microsoft AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

### Gaps

- No measured JIT/R2R/AOT comparison exists here for the actual viewer, F# dependencies, target hardware, or PDF corpus. No numerical startup estimate should be copied into the final recommendation.
- The FuncUI control-catalog AOT release note concerns an older release; latest FuncUI 2.0 + Avalonia 12.1 + the eventual PDF wrapper still needs real publish-and-run verification.
- Official F# templates exist, but this research did not establish equal designer, hot-reload, editor completion, or C# source-generator support in every F# toolchain. Test the actual editor and workflow the maintainer will use.
- The project has no selected PDF rendering binding yet, so UI-toolkit AOT support alone cannot establish whole-application AOT viability.

## 2. How do GTK/.NET, Qt/C++, Windows-only frameworks, MAUI, and webviews compare?

### Takeaway

**Avalonia remains the best first fit for the stated F# + Windows/Linux + modest-maintenance constraints.** GTK/.NET is attractive if Linux integration dominates, Qt Widgets/C++ is a serious native alternative if the user accepts a language/toolchain change, and neither Windows-only UI frameworks nor official MAUI currently satisfy both required desktop platforms. Webviews are worth considering for reuse of an existing web viewer, not assuming they are inherently unacceptable or inherently fast.

### Cited Findings

#### GTK bindings for .NET/F#

- **GtkSharp is a separate project from the older Mono gtk-sharp.** Its README describes a C# wrapper targeting .NET Standard 2.0 and GTK 3.22, with GTK/GLib/GIO/Cairo/Pango/ATK/GDK-related packages; it is not a GTK4 binding. Its wrapper/components are described as LGPL v2.0. [GtkSharp README](https://github.com/GtkSharp/GtkSharp)
- GtkSharp's GitHub releases feed tops out at 3.24.24.34 from April 2021, but NuGet contains later stable 3.24.24.95 and development versions through 3.24.24.133-develop. The commit API shows an August 2025 merge. Therefore “last GitHub release 2021” is **not** sufficient evidence that development stopped in 2021; conversely, these sources do not demonstrate a brisk 2026 maintenance cadence. [GitHub releases](https://api.github.com/repos/GtkSharp/GtkSharp/releases?per_page=4), [NuGet index](https://api.nuget.org/v3-flatcontainer/gtksharp/index.json), [Recent commits](https://api.github.com/repos/GtkSharp/GtkSharp/commits?per_page=3)
- **GirCore** provides C# bindings for GObject libraries including GTK4, libadwaita, WebKitGTK, and GStreamer. The project explicitly states it supplies **bindings, not the native C libraries**; those must be installed/bundled separately. [GirCore home](https://gircore.github.io/), [Getting started / required binaries](https://gircore.github.io/docs/get-started.html)
- GirCore 0.8.1 is a non-prerelease from 2026-07-12, and 0.9.0-preview.1 was published 2026-09-15. The 0.8 line adds composite-template support and has breaking changes to subclass/instance creation; 0.8.1 includes fixes in source-generated subclasses and initialization. It is actively developing, but a pre-1.0 API should not be described as frozen. [0.8.1](https://github.com/gircore/gir.core/releases/tag/0.8.1), [0.8.0](https://github.com/gircore/gir.core/releases/tag/0.8.0), [0.9 preview](https://github.com/gircore/gir.core/releases/tag/0.9.0-preview.1)
- GirCore's documented custom GObject-subclass/template path uses **C# partial classes and source generators**, attributes, unsafe generated integration, and factory initialization instead of normal constructors. Calling the generated CLR API is different from authoring these subclasses entirely in F#. [GirCore subclassing/templates](https://gircore.github.io/docs/get-started.html)
- GTK4 has native Win32, X11, and Wayland backends, subject to what the GTK binary was built to include. `GDK_BACKEND` can select/test backends. Toolkit support does not guarantee that a particular .NET binding package or distributed native bundle supports every backend/version combination. [GTK runtime/backend documentation](https://docs.gtk.org/gtk4/running.html)

#### Qt Widgets/C++

- Qt's own documentation describes its Linux/X11 support as extensive/mature and lists supported compiler/distribution combinations. Its Windows deployment tool `windeployqt` assembles Qt libraries, plugins, translations, and relevant compiler runtime files; additional third-party libraries can still need separate handling. Native does not mean “one executable with no dependencies.” [Qt Linux](https://doc.qt.io/qt-6.8/linux.html), [Windows deployment](https://doc.qt.io/qt-6.8/windows-deployment.html)
- Qt PDF uses PDFium, provides document/page rendering, navigation, search, bookmarks, and links, and includes `QPdfView`, described as a complete PDF viewer widget. This is a material implementation-effort advantage over a GUI shell plus only a raw PDF rasterizer. A Qt PDF API does not imply embedding a Chromium browser UI. [Qt PDF 6.8 documentation](https://doc.qt.io/qt-6.8/qtpdf-index.html)
- Qt is offered commercially and under open-source licenses, chiefly LGPLv3/GPLv3, with some modules GPL-only under open-source terms. **Do not state “Qt requires buying a license,” and do not state “all Qt modules are LGPL.”** The versioned Qt PDF page specifically lists commercial, LGPLv3, or GPLv2 terms for that module; inspect exact module/version and third-party notices. [Qt licensing](https://doc.qt.io/qt-6/licensing.html), [Qt PDF licensing summary](https://doc.qt.io/qt-6.8/qtpdf-index.html)
- Qt's LGPL obligations guide says proprietary application code can remain closed if all applicable LGPL obligations are met; it discusses library source availability, notices, user modification/relinking, installation information, and distribution restrictions. Dynamic linking is generally the simpler compliance route, not a substitute for meeting the other obligations. Get legal review where necessary. [Qt open-source obligations](https://www.qt.io/licensing/open-source-lgpl-obligations)
- .NET's supported low-level native interop mechanism imports native functions and handles structures/callbacks. It is not a direct bridge to arbitrary C++ class APIs. NativeAOT also excludes C++/CLI. [P/Invoke](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke), [NativeAOT limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

#### WPF, WinUI, and MAUI

- **WPF remains Windows-only** even on modern cross-platform .NET. It has mature XAML, layout, binding, and control facilities, but a WPF shell is not the same Windows/Linux UI implementation. [Microsoft WPF overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)
- **WinUI 3** is Microsoft's recommended native UI framework for new Windows desktop apps, delivered through the Windows App SDK, with documented C#/C++ development and support for Windows 10 1809 onward. It is not a native Linux backend or an F#-first project model in that documentation. [Microsoft WinUI 3 overview](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/)
- The current official **MAUI supported-platforms** page lists Android, iOS, Mac Catalyst, and Windows; it separately mentions Samsung-provided Tizen support, but **does not list Linux**. The fetched documentation includes .NET 11 monikers as well as .NET 10, which is not proof of a released .NET 11 or official Linux support. Community Linux backends/forks must be judged independently and should not be presented as first-party supported MAUI Linux. [Microsoft supported platforms](https://learn.microsoft.com/en-us/dotnet/maui/supported-platforms?view=net-maui-10.0)

#### Webview options

- **Electron** inherits Chromium's multiprocess architecture: a Node.js main process manages windows and each `BrowserWindow` has a renderer process. That is documented structure, not a measured startup time or RAM number. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model)
- **System webviews** avoid requiring the app to ship its own entire browser engine in some deployment modes, but still need the engine at runtime. Tauri's docs identify WebView2 on Windows and WebKitGTK on Linux; they explicitly say Linux WebKit versions vary by distribution and its version table is incomplete. Tauri also has a Rust-facing backend/toolchain, so it is not the default recommendation for someone who specifically wants to avoid Rust compilation. [Tauri webview backends](https://v2.tauri.app/reference/webview-versions/)
- **WebView2 deployment** requires the WebView2 Runtime, not merely the installed Edge Stable browser. Microsoft's guide describes a shared auto-updated Evergreen runtime, availability checks/installation, and an application-bundled Fixed Version whose updates the app owner must ship. Thus a small application installer may externalize a substantial runtime dependency rather than eliminate it. [Microsoft WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

[Electron](https://www.electronjs.org/docs/latest/tutorial/process-model), [WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution), [Linux webview variability](https://v2.tauri.app/reference/webview-versions/) |

- **Do not conflate bundle size, installed size, resident memory, and startup.** A shared system webview can reduce shipped bytes yet still initialize a browser engine; a self-contained native build can be larger on disk yet remove JIT. Benchmark each metric separately. [WebView2 deployment](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution), [.NET publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/)
- **Webviews may help feature completeness but hurt architectural simplicity for this particular brief.** They add another UI/runtime boundary around an F# core; they are more persuasive if reusing a proven viewer rather than building a browser shell solely to display rasterized pages. This is a project-fit inference, not a universal claim that native beats web. [Electron process boundaries](https://www.electronjs.org/docs/latest/tutorial/process-model), [Webview engine differences](https://v2.tauri.app/reference/webview-versions/)
- **Uncluttered UX is a product decision, not a benchmark category a framework wins automatically.** Proposed shell: one compact toolbar, page/zoom controls, keyboard shortcuts, optional search/sidebar, and a central page canvas; no ribbon, onboarding, account, or network initialization on the opening path. Any shortlisted general UI toolkit can be evaluated against that same design; do not compare a minimal prototype to a feature-heavy viewer and attribute the entire difference to its language.

### Gaps

- This research did not verify a current officially supported end-to-end **F#** GirCore subclass/AOT sample. Its documented C# generator workflow should be treated as a real integration question, not silently assumed to work unchanged in F#.
- No blanket AOT certification was established for GtkSharp, GirCore, a .NET-hosted Linux webview wrapper, or arbitrary .NET Qt bindings. Validate package/version-specific claims before choosing them.
- Native Qt Wayland packaging was not investigated to a feature-by-feature level here; if Qt becomes a finalist, verify the selected Qt version's Wayland platform plugin, compositor behavior, PDF module distribution, and support matrix.
- Qt's rolling `/qt-6/` documentation identified a newer documentation set than the version-pinned 6.8 pages. No claim is made here about the latest **released** Qt version based only on a documentation header; 6.8 links provide concrete established feature/licensing evidence, not a recommendation to choose that exact branch indefinitely.
- The Tauri backend page contains historical Windows-version wording. It is cited for backend architecture, not as an authoritative 2026 Windows support/security matrix; use Microsoft's current WebView2 documentation for deployment support decisions.

## 3. What should be benchmarked and shipped, especially on Linux/X11/Wayland?

### Takeaway

**Build a minimal published vertical slice before choosing an optimization mode: empty shell, real first PDF page, then navigation/zoom.** Compare ordinary JIT, ReadyToRun, and NativeAOT using the same UI/rendering path on real Windows and Linux systems; ship the least complicated option that meets the measured experience. Separate native system dependencies, packaging, runtime servicing, and compositor support from the choice of managed compilation mode.

### Cited Findings

#### .NET publishing choices and what they actually mean

- **Framework-dependent:** requires an installed compatible .NET runtime and distributes fewer runtime files; runtime patch roll-forward is part of its deployment model. **Self-contained:** includes the selected .NET runtime, does not need preinstallation, but still requires native OS dependencies and must be republished to service the bundled runtime. Explicitly choose self-contained status rather than relying on changing SDK defaults or treating `-r` alone as a guarantee. [Microsoft publishing overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/)
- **ReadyToRun:** includes native code alongside IL to reduce startup JIT work. Microsoft warns larger assemblies can increase disk-loading work/working set, and small applications may see little benefit because framework libraries are already precompiled. Some methods still JIT, and tiered compilation can replace R2R code. “AOT” in “R2R is a form of AOT” does **not** mean NativeAOT's no-JIT execution model. [Microsoft R2R documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run)
- **Composite R2R** has longer compilation and greater output-size tradeoffs and is recommended only for particular scenarios; do not make it the initial default merely because startup matters. [Microsoft composite R2R guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run)
- **NativeAOT:** no runtime JIT, self-contained, platform/architecture-specific, additional native compiler prerequisites, trimming/dependency restrictions, and longer publishing work than a regular managed build. Microsoft describes startup/memory benefits in general; this is not a measurement for an Avalonia PDF viewer. Build on Windows for Windows and Linux for Linux as the conservative CI plan, using an appropriate old-enough Linux baseline. [NativeAOT prerequisites and limitations](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [Publishing tradeoffs](https://learn.microsoft.com/en-us/dotnet/core/deploying/)
- **Single-file is packaging, not synonymous with AOT or zero extraction.** Managed assemblies can load from the bundle without disk extraction, while native libraries can remain adjacent or be embedded for self-extraction. `IncludeNativeLibrariesForSelfExtract` causes native-library extraction; `IncludeAllContentForSelfExtract` extracts more content. Compression adds startup decompression cost and Microsoft explicitly recommends measuring it. [Detailed single-file documentation](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)
- Microsoft's general publishing overview summarizes single-file as involving extraction, but the detailed single-file page describes the actual conditional native-library extraction behavior. Prefer the detailed explanation; do not claim every current single-file .NET app unpacks all assemblies on every launch. [Overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [Detailed behavior](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)

#### Current Avalonia Linux facts

- Avalonia uses **X11 by default**. In Wayland desktop sessions, that default path runs through **XWayland**. A native Wayland backend exists from **12.1.0**, distributed as `Avalonia.Wayland`, but is explicitly early-stage and not automatically selected by `UsePlatformDetect()`. `UseWayland()` has no automatic fallback and cannot start without a Wayland compositor. [Avalonia Linux/Wayland documentation, updated 2026-10-09](https://docs.avaloniaui.net/docs/platform-specific-guides/linux)
- Current native-Wayland docs describe mouse/touch/keyboard, clipboard, and drag/drop support; rendering uses OpenGL/OpenGL ES through EGL. They also list missing KDE global-menu/window-icon/blur integrations. These are documented capabilities/limitations, not assurance that the eventual viewer's IME, portals, accessibility, scaling, and shortcuts all behave correctly on every compositor. [Wayland features and limitations](https://docs.avaloniaui.net/docs/platform-specific-guides/linux)
- Avalonia's X11 renderer configuration supports ordered backends and documents software fallback, recommending it for broader coverage including remote sessions/VMs. [Linux rendering modes](https://docs.avaloniaui.net/docs/platform-specific-guides/linux)
- The current platform page lists X11-path dependencies `libx11-6 libice6 libsm6 libfontconfig1`. It says Skia is built against glibc 2.17, while musl distributions need a custom `libSkiaSharp.so` build and fall into Tier 3. **This is not a claim the entire .NET 10/PDF app runs on any glibc 2.17 machine**: the runtime, PDF engine, and other native libraries can impose a newer minimum. [Avalonia supported platforms](https://docs.avaloniaui.net/docs/supported-platforms)
- The October 2026 Avalonia platform matrix lists Ubuntu 25.x, Fedora 43, and Debian 13 among Tier 1 desktop-Linux combinations; Ubuntu through 24.x, Fedora through 42, and Debian through 12 are listed Tier 2. Tier 1 means release-tested/supported; Tier 2 is best effort; unlisted distributions are Tier 3/commercial support only. It would be misleading to silently describe every commonly used distro as equally supported. [Exact platform tiers](https://docs.avaloniaui.net/docs/supported-platforms)
- Windows support also has tiers: that page lists Windows 11 24H2 x64/ARM64 as Tier 1 and Windows 10 22H2 x64 as Tier 2. The application support promise must be the **intersection** of toolkit, .NET, PDF engine, OS, architecture, and actually tested configurations, not any single vendor's matrix. [Avalonia Windows matrix](https://docs.avaloniaui.net/docs/supported-platforms), [.NET supported-OS metadata link](https://dotnetcli.blob.core.windows.net/dotnet/release-metadata/releases-index.json)
- NativeAOT binaries produced on a newer Linux baseline may not work on older Linux installations. Microsoft explicitly advises compatibility with the same or newer Linux version than the build baseline. Avalonia self-contained output also includes native Skia/HarfBuzz libraries, and the PDF engine adds its own platform assets. [Microsoft AOT Linux baseline](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [Avalonia deployment layout](https://docs.avaloniaui.net/docs/deployment/linux)
- Avalonia's Linux deployment guide documents `.deb` packaging, desktop entries, icons, executable permissions, and forwarding file-open arguments via `%F`. It refers to .NET 8 dependency examples; use them as a packaging pattern, **not** an exact .NET 10 dependency list. [Linux packaging guide](https://docs.avaloniaui.net/docs/deployment/linux)

### Inferences

#### Proposed experiment matrix — recommendations, not executed benchmarks

1. **Freeze inputs:** one SDK/toolkit/PDF-engine version set, identical Release configuration, same fonts and theme, same page size/zoom, and identical functional scope. Start with the official F# plain-XAML shell; compare a FuncUI shell only if still deciding UI style. Record the operating system, compositor/session type, GPU driver, storage, CPU, power profile, and runtime distribution. This prevents comparing different applications under the label “framework benchmark.” [Official F# templates](https://github.com/AvaloniaUI/Avalonia.Templates), [Platform/backend variability](https://docs.avaloniaui.net/docs/platform-specific-guides/linux)
2. **Keep compilation and packaging separate:** first compare folder-published framework-dependent JIT, self-contained JIT, self-contained R2R, and self-contained NativeAOT. Then compare equivalent single-file/extraction/compression variants only if packaging requirements justify them. Mark NativeAOT unavailable if the dependency graph cannot be made reliable; do not hide warnings and call it supported. [Publishing modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [R2R](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run), [Single-file](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), [AOT analysis](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
3. **Measure distinct milestones from external process launch:** (a) first visible shell frame, (b) first correctly rendered PDF page actually presented, (c) first successful input/scroll/zoom response, (d) jump to an uncached distant page. Record internal phases too: managed entry, UI setup, native PDF load, document open, first-page rasterization, upload/composition/presentation. A visible empty window is not “viewer loaded.” These are proposed acceptance metrics, not sourced performance values.
4. **Separate cold cases:** first launch after installation/update; fresh process with warm OS caches; genuinely cold/rebooted or controlled-VM runs; first-ever user/font/native-extraction caches. Do not label a repeatedly launched process with warm file caches “cold start.” Count any retained background instance separately and do not use prewarming as a hidden startup optimization. Publish the methodology with results.
5. **Use a representative local corpus:** tiny text, ordinary multipage document, scanned/image-heavy pages, complex vector/fonts, long document with bookmarks/search, and a larger file; add malformed/encrypted cases for reliable failure behavior. Keep the same engine/corpus for UI comparisons. If comparing Qt PDF against another engine, label it a whole-stack comparison rather than pure GUI overhead. [Qt PDF's integrated engine/features](https://doc.qt.io/qt-6.8/qtpdf-index.html)
6. **Collect distributions, not one best run:** report sample counts, median/tail startup, peak and settled process-tree memory, CPU/I/O, package download bytes, installed bytes, and first/clean/incremental/publish build durations. Count child processes for webview solutions. Define the user's acceptable first-page latency before selecting the winner; no arbitrary measured-looking target is supplied here. [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [AOT/R2R build and size tradeoffs](https://learn.microsoft.com/en-us/dotnet/core/deploying/)
7. **Profile bottlenecks before switching frameworks:** if first-page time is mostly PDF parse/raster or font/graphics initialization, removing JIT may not solve it. Prioritize opening/rasterizing the visible page, defer thumbnails/bookmark trees/search indexing, cancel obsolete zoom/page renders, and bound caches. These are proposed architecture choices; validate that they help rather than reporting hypothetical savings. [R2R's specifically JIT-related mechanism](https://learn.microsoft.com/en-us/dotnet/core/deploying/ready-to-run), [Qt PDF render-queue example architecture](https://doc.qt.io/qt-6.8/qtpdf-index.html)
8. **Test real deployment:** launch published apphosts, not `dotnet run`, debugger startup, hot reload, or a development server. Use a clean machine without SDK/runtime for self-contained/AOT validation. Measure the installed package with normal user security software rather than only the build folder. [.NET publish/apphost guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/)

#### Suggested release and maintenance plan

- **First distribution:** separate `win-x64` and `linux-x64` self-contained folder outputs, archived or packaged; add ARM64 only when there is demand and native PDF assets plus test hardware exist. Evaluate R2R as a low-disruption optimization and NativeAOT as an optional measured improvement. Keep ordinary fast managed builds for the edit/run loop even if releases use AOT, respecting the user's concern about compile-time friction. [RID/native-asset publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [AOT prerequisites](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
- **Linux support contract:** explicitly choose a small set of .NET-supported glibc-based desktop distributions, ideally covering the intended users and acknowledging Avalonia's tiers. CI can build on the oldest supported baseline; real/VM desktop smoke tests must cover X11, GNOME Wayland via XWayland, KDE Wayland via XWayland, and separately the opt-in native-Wayland path if offered. A native Wayland toggle should not silently replace the proven default on all machines. [Avalonia tiers](https://docs.avaloniaui.net/docs/supported-platforms), [Wayland caveats](https://docs.avaloniaui.net/docs/platform-specific-guides/linux), [AOT baseline guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
- **Dependency audit:** derive distro package dependencies from the actual .NET version and native library closure. Include graphics/font libraries, selected PDF library, any C/C++ runtime requirements, and portals/session services used by integration. Check the installed artifact on clean desktops; self-contained .NET is not a universal statically linked Linux binary. Do not copy a legacy dependency list wholesale. [.NET native dependencies](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [Avalonia dependencies/package guide](https://docs.avaloniaui.net/docs/deployment/linux)
- **Integration smoke tests:** file association/open-with; file paths with spaces/Unicode; multiple file arguments; drag/drop; clipboard; keyboard focus/shortcuts; portal file picker; high-DPI and fractional scaling; mixed-monitor moves; printing if included; accessibility; GPU failure/software fallback. Linux screenshots under WSL are useful development checks but not a replacement for the intended compositor/distro test matrix. [Avalonia Linux platform services and accessibility](https://docs.avaloniaui.net/docs/platform-specific-guides/linux), [Desktop/file-argument packaging](https://docs.avaloniaui.net/docs/deployment/linux)
- **Package formats:** start with a small supported scope, e.g. Windows portable folder/installer and Linux `.deb` plus a documented tarball; add `.rpm`, Flatpak, or AppImage only when their target audience/dependency/sandbox tradeoffs justify the extra testing. This is a scope recommendation, not a claim that any format automatically solves native-library compatibility. [Avalonia Linux packaging](https://docs.avaloniaui.net/docs/deployment/linux)
- **Service native and managed dependencies:** pin reproducible versions, keep runtime/PDF-engine/graphics security updates on a routine schedule, retain symbols for crash analysis, and run the first-page/native-library smoke tests on each update. Self-contained/AOT releases transfer runtime patch shipping to the application maintainer; NativeAOT does not sandbox an in-process PDF parser. [Runtime servicing model](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [NativeAOT symbols](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)

### Gaps

- No quantitative answer yet to “will it open without multi-second loading?” The selected PDF engine, first-page rendering path, disk/cache state, graphics stack, and published configuration determine that; an instrumented prototype is required.
- No exact Linux package dependency manifest is supplied because it must follow the chosen .NET/PDF/native-graphics versions and target distro. The Skia glibc statement is only one component's minimum, not the application's support floor.
- Native Wayland exists today but is early-stage; a complete feature-parity and compositor reliability audit for this app is still outstanding.
- Flatpak/AppImage/installer tools, code-signing arrangements, and automatic updates were not validated in this research. They should remain explicit delivery decisions rather than hidden assumptions.
- The recommendation intentionally does **not** default to Rust. No language/framework is awarded invented millisecond startup or compile-time figures; even the Qt native alternative must earn its complexity through measured results and implementation savings.
