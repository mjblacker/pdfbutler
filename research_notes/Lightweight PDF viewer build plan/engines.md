# PDF engines and a minimal F# viewer boundary

Research date: **3 November 2026**. Scope: a fast, read-only Windows/Linux desktop viewer with basic Acrobat Reader usability, not an editor. Primary documentation, upstream headers and project repositories were fetched directly; web-search requests failed. Version/activity observations below are dated snapshots, not guarantees of package quality or security. Recommendations are explicitly separated from documented capabilities. No implementation or performance benchmark was performed.

## 1. Which engines, .NET bindings and licensing models fit?

### Takeaway

**Start the technical evaluation with PDFium, using a current, thin .NET binding and a controlled native distribution.** MuPDF is a serious alternative if its AGPL/commercial licensing and binding/update story fit; Poppler fits GPL-compatible products but brings a less direct .NET integration; PDF.js is attractive when accepting a web runtime and reusing its existing viewer UI is preferable to building native selection/search/navigation.

### Cited Findings

| Engine / integration | Documented facts | Decision implications, not benchmark results |
| --- | --- | --- |
| **PDFium** | Native C API for opening, page rendering, text, links, bookmarks and forms. Headers document process-wide initialization and non-thread-safe APIs. The current LICENSE contains the BSD-style redistribution terms **and Apache-2.0 text**; third-party components have their own notices. [Main API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [LICENSE](https://github.com/chromium/pdfium/blob/main/LICENSE), [binary-distributor license collection](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/08-licenses.sh). | Strong first candidate for a native .NET viewer; not a ready-made cross-platform viewer control. Do not infer that embedding PDFium includes Chrome's sandbox or UI. |
| **MuPDF** | Native rendering/document library, available under **GNU AGPL or a commercial Artifex license**. Official generated C++ and C# APIs exist; C# is generated via SWIG from the C++ layer. [License](https://mupdf.readthedocs.io/en/latest/license.html), [official C# bindings](https://mupdf.readthedocs.io/en/latest/reference/cxx-and-derived-bindings.html). | Evaluate seriously when licensing is acceptable. Its useful display-list/multithreading model is not permission to access one document concurrently. Official binding existence is not proof of a turnkey, current NuGet desktop-viewer package. |
| **Poppler** | Upstream explicitly says **GPL, not LGPL** and warns that programs calling Poppler must meet GPL requirements. Upstream offers cpp, glib, qt5 and qt6 frontends, not an official .NET frontend on its documentation list. [Upstream README mirror](https://github.com/tsdgeos/poppler_mirror/blob/master/README.md), [official project/API list](https://poppler.freedesktop.org/). | Reasonable engine for a GPL-compatible viewer, especially on Linux. A C GLib bridge or a native shim is an integration option; Windows dependency packaging and binding maintenance need a separate audit. Do not mistake a Poppler command-line package for a complete in-process viewer API. |
| **PDF.js** | Mozilla's HTML5/JavaScript PDF viewer/parser/renderer; prebuilt distribution is `pdfjs-dist`. Apache-2.0 project license. API uses workers and browser rendering facilities; viewer source includes find and text-layer controllers. [Project](https://github.com/mozilla/pdf.js), [license](https://github.com/mozilla/pdf.js/blob/master/LICENSE), [API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [find controller](https://github.com/mozilla/pdf.js/blob/master/web/pdf_find_controller.js), [text layer](https://github.com/mozilla/pdf.js/blob/master/web/text_layer_builder.js). | A different architecture: host a local HTML viewer in a supported web runtime, not a normal F# P/Invoke renderer. Existing viewer behavior can save substantial UI work; web-runtime startup, deployment and memory must be measured on both OSes, not assumed acceptable or unacceptable. |

**Concrete .NET/native distribution candidates and cautions:**

- **PDFiumCore (`Dtronix/PDFiumCore`)** documents .NET Standard 2.1 generated P/Invoke bindings and included bblanchon native binaries, with Linux-x64, Windows-x64/x86 and macOS-x64 listed. Its wrapper license is **Apache-2.0**. The GitHub latest-release API returned `v158.0.8125.0`, published **2026-11-01**, demonstrating recent releases, not feature completeness or an independent security audit. Native library inclusion does not remove the caller's scheduling/lifetime obligations. [README](https://github.com/Dtronix/PDFiumCore), [release snapshot endpoint](https://api.github.com/repos/Dtronix/PDFiumCore/releases/latest).
- **DtronixPdf** is a higher-level .NET 8 MIT-licensed layer over PDFiumCore. Its README explicitly serializes all PDFium calls onto one dispatcher thread and returns Tasks; listed desktop architectures match the README above. Latest release observed was `v1.3.1.0`, **2025-03-24**. Useful to inspect or trial for its ownership/scheduling design; do not claim that its viewer APIs, cancellation or forms meet all requirements without a spike. [README](https://github.com/Dtronix/DtronixPdf), [release endpoint](https://api.github.com/repos/Dtronix/DtronixPdf/releases/latest).
- **bblanchon/pdfium-binaries** is an independent native binary distributor, expressly unaffiliated with Google/Foxit. It documents automated Monday builds since 2017, Windows and Linux variants including ARM64 and glibc/musl combinations, plus `bblanchon.PDFium`, `.Linux`, `.Win32` and separate V8 packages. Current latest-release observation: `chromium/8125`, **2026-10-26**. Its published artifacts are dynamic libraries; this is distribution, not a .NET viewer abstraction. **The distributor's MIT repository license does not replace PDFium/dependency licenses.** [README/platform and NuGet tables](https://github.com/bblanchon/pdfium-binaries), [release endpoint](https://api.github.com/repos/bblanchon/pdfium-binaries/releases/latest), [license collection script](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/08-licenses.sh).
- That distributor's configure script sets both `pdf_enable_v8` and `pdf_enable_xfa` from the V8 option, which defaults false. Thus its ordinary non-V8 flavor is a concrete starting point for a no-document-JavaScript/no-XFA policy; confirm the chosen artifact's actual build settings. Do not generalize these flags to every PDFium distributor. [Build configuration](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/05-configure.sh).
- **PDFiumSharp (`ArgusMagnus/PDFiumSharp`)** is a real managed wrapper, but its README foregrounds Windows binaries, GDI+/WPF extensions and raw memory bitmaps. The wrapper's LICENSE is **Microsoft Reciprocal License (MS-RL)**, not PDFium's engine license. GitHub metadata showed last push **2023-11-14**. Do not recommend it as the default maintained Windows/Linux solution merely from its name or an old tutorial. [README](https://github.com/ArgusMagnus/PDFiumSharp), [MS-RL LICENSE](https://github.com/ArgusMagnus/PDFiumSharp/blob/master/LICENSE), [repository metadata](https://api.github.com/repos/ArgusMagnus/PDFiumSharp).
- **Original PdfiumViewer (`pvginkel/PdfiumViewer`) is archived** according to repository metadata. Distinguish this project from differently maintained forks/packages with similar names; an archived Windows-viewer example is not evidence of a supported cross-platform solution. [Repository metadata](https://api.github.com/repos/pvginkel/PdfiumViewer).
- **MuPDF's official generated C# bindings** document Windows/Linux build procedures, C# exceptions, automatic reference counting and some omitted APIs. The documentation does not establish a matching official all-platform NuGet release pipeline; evaluate the native build/packaging burden explicitly. [Official binding documentation](https://mupdf.readthedocs.io/en/latest/reference/cxx-and-derived-bindings.html).
- **MuPDFCore (`arklumpus/MuPDFCore`)** documents .NET Standard 2.0, an Avalonia rendering control, multithreaded rendering, native-asset packages for Windows x86/x64/ARM64 and Linux x64/ARM64 glibc/musl, and **AGPLv3 for the wrapper**. Its README says version 2 uses a MuPDF fork based on **1.25.2**; latest observed release was `v2.0.1`, **2025-01-06**, and last push **2025-08-17**. Meanwhile fetched official MuPDF docs identified themselves as **1.28.5**. This is a concrete reason to audit native patch lag, not a claim that the package is necessarily vulnerable. Buying an engine license does not automatically relicense an independently AGPL wrapper. [README](https://github.com/arklumpus/MuPDFCore), [release endpoint](https://api.github.com/repos/arklumpus/MuPDFCore/releases/latest), [repository metadata](https://api.github.com/repos/arklumpus/MuPDFCore), [current official docs](https://mupdf.readthedocs.io/en/latest/).
- **PdfPig is not a drop-in full renderer.** It describes reading text/content and basic PDF creation; its README has text, glyph geometry, links, bookmarks, passwords and read-only form extraction. Those are valuable extraction features, not a replacement for full page painting, font/image decoding, transparency and annotation/form appearance rendering. The README itself warns that internal content order is rarely the desired reading order. [PdfPig README](https://github.com/UglyToad/PdfPig).

**Licensing precision:**

- Preserve the exact pinned PDFium LICENSE plus relevant bundled dependency licenses/notices and the managed wrapper's license. Older shorthand such as “PDFium is BSD” does not describe every file or every current binary's complete notice set. The binary distributor scans linked third-party libraries and separately includes V8 licenses when enabled, illustrating why build options matter. [PDFium LICENSE](https://github.com/chromium/pdfium/blob/main/LICENSE), [third-party notice staging](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/08-licenses.sh).
- MuPDF's own licensing page explicitly offers AGPL and commercial paths. Poppler's README explicitly distinguishes it from LGPL and says a commercial **Xpdf** license is not a license for **Poppler**. Treat these as upstream licensing positions; do not promise that putting either library in a helper process, dynamically linking it, distributing only internally, or choosing a permissive wrapper universally resolves obligations. Actual assessment depends on versions, integration, distribution, modifications and applicable law/contracts. [MuPDF licensing](https://mupdf.readthedocs.io/en/latest/license.html), [Poppler licensing statement](https://github.com/tsdgeos/poppler_mirror/blob/master/README.md).

### Inferences

- Recommended shortlist: **PDFiumCore plus a small owned F# adapter**, with DtronixPdf inspected as an alternative to owning dispatch/ownership plumbing. **MuPDF with an approved licensing path** is the alternative to benchmark, rather than adding a second production engine immediately. This is a fit/complexity judgment based on the documented C/.NET APIs and packaging above, not a speed ranking.
- If the project will be GPL/AGPL-compatible anyway, licensing alone need not eliminate Poppler/MuPDF. Conversely, if distribution requirements are undecided, keep that decision open before selecting a wrapper with additional reciprocity obligations. [Engine/wrapper sources above](https://mupdf.readthedocs.io/en/latest/license.html), [PDFiumSharp license](https://github.com/ArgusMagnus/PDFiumSharp/blob/master/LICENSE).
- Reusing PDF.js's viewer is worth considering if native text-selection/UI implementation dominates the effort, but a minimal native desktop viewer should not gain an embedded browser simply on an unsupported claim that one renderer is “fastest.” [PDF.js viewer project](https://github.com/mozilla/pdf.js).

### Gaps

- No comparable, current end-to-end Windows/Linux cold-start/time-to-first-page benchmark was found or executed. Do not quote invented millisecond figures, throughput rankings, memory figures or bundle sizes.
- Package architecture lists above are **README claims**, not publication tests. Need to inspect the selected `.nupkg`, its actual native revision/export set, build flags, transitive assets, license files and minimum platform/runtime dependencies.
- This pass did not establish a clearly maintained, complete Poppler .NET viewer binding suitable for both Windows and Linux. That is an evidence gap, not proof none exists. The official frontend list is the reliable starting point. [Official API list](https://poppler.freedesktop.org/).

## 2. What basic-reader features, rendering pitfalls and concurrency constraints matter?

### Takeaway

All four engines expose substantial reading capabilities, but **page rasterization alone is not basic-reader usability**. Text geometry/selection, search, link/outline interpretation, password retry and visible form appearances must be verified through the chosen binding; PDFium in particular requires serialization across **all** documents in a process, not just per-document locks.

### Cited Findings

| Requirement | PDFium | MuPDF | Poppler | PDF.js |
| --- | --- | --- | --- | --- |
| **Text selection/copy and search** | `FPDFText_LoadPage`, character geometry/hit testing, text extraction, `FPDFText_FindStart/Next/Prev`, result ranges and rectangles provide building blocks; app supplies selection behavior and highlights. [Text API](https://github.com/chromium/pdfium/blob/main/public/fpdf_text.h). | Structured text exposes search, selection snapping, highlight quadrilaterals and copy-selection/rectangle helpers. [Structured-text header](https://github.com/ArtifexSoftware/mupdf/blob/master/include/mupdf/fitz/structured-text.h). | GLib exposes find-text options, selected text/regions and character layout. [Page API](https://poppler.freedesktop.org/api/glib/poppler-Poppler-Page.html). | `getTextContent` plus text-layer/find-controller viewer components; drawing a canvas alone does not provide selectable text. [API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [text layer](https://github.com/mozilla/pdf.js/blob/master/web/text_layer_builder.js), [find controller](https://github.com/mozilla/pdf.js/blob/master/web/pdf_find_controller.js). |
| **Links and outline/bookmarks** | `FPDFLink_*`, `FPDFBookmark_*`, destinations and typed actions; also optional detected text URLs. XFA is build-dependent and separate. [Rendering API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [forms API](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h). | Widget/field inspection and form APIs; document API separates main content, annotations and widgets when desired. [Rendering/loading options](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [field APIs](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js). |

- **Read-only must still display filled forms.** PDFium explicitly says `FPDF_RenderPageBitmap` with `FPDF_ANNOT` does not draw widget annotations, and `FPDF_FFLDraw` must follow completed page rendering. Initializing an appropriately configured form environment and its page lifecycle may therefore be necessary even when input events, editing and saving are absent. Do not equate “no form editing” with “ignore form rendering.” [Main rendering header](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [form-fill lifecycle and draw documentation](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h).
- **PDFium thread safety is process-wide at the API boundary.** The authoritative header says “None of the PDFium APIs are thread-safe,” expects one thread, or a mutex ensuring only one call at a time. This applies to separate documents, text/search work, thumbnail rendering and disposal just as much as normal pages. The same header calls initialization configuration process-wide, describes global resource allocation/destruction, and says destruction does not close existing objects. [Main API header](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h).
- DtronixPdf's documented design uses a single dispatcher for all PDFium calls, providing a concrete .NET example of the required discipline rather than relying on unrelated Tasks or one lock per document. [DtronixPdf README](https://github.com/Dtronix/DtronixPdf).
- **MuPDF's concurrency model differs but has rules:** no simultaneous use of the same context, document or device; provide shared locking callbacks and clone a base context. A document-owner thread can produce display lists that other threads render concurrently with appropriate contexts. Independent contexts do not justify unrelated locking schemes. [Official C overview / multithreading](https://mupdf.readthedocs.io/en/latest/reference/c/overview.html).
- **Cancellation is cooperative, not arbitrary native-call interruption.** PDFium progressive rendering provides pause callbacks, continue calls and render-close cleanup. `FPDF_LoadDocument`, ordinary bitmap rendering and text APIs do not expose a general .NET cancellation-token parameter. A canceled managed Task cannot by itself stop an active native call. [Progressive API](https://github.com/chromium/pdfium/blob/main/public/fpdf_progressive.h), [open/render API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h).
- MuPDF's render `fz_cookie.abort` is checked periodically, and the header explicitly says there is **no upper bound** on when rendering aborts. Cookie communication is described as unsynchronized without locking. Use the chosen wrapper's supported mechanism, not an assumed immediately effective token. [Cookie definition and contract](https://github.com/ArtifexSoftware/mupdf/blob/master/include/mupdf/fitz/device.h).
- PDF.js `RenderTask.cancel` also waits for a rendering pause; loading-task destruction tears down transport/workers. Browser workers are not equivalent to OS security sandboxes. [RenderTask documentation](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-RenderTask.html), [loading-task/worker implementation](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js).
- **Rendering details affect correctness:** PDFium distinguishes non-premultiplied BGRA from an experimental Skia-only premultiplied format, exposes crop/media intersections and device/page transforms, and has explicit annotation and antialiasing flags. PDF.js documents fallback-font behavior, packaged CMaps/standard fonts/ICC/WASM assets, and recovery-vs-stop-at-errors behavior. Those settings can change both appearance and work performed. [PDFium bitmap/geometry API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [PDF.js initialization options](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html).
- **Engine maturity is not universal fidelity.** The official Poppler 26.10.0 release notes include form rendering fixes, malformed-document crash fixes and font/backend changes. PdfPig explains why content stream order is not necessarily reading order. These are concrete reasons for a document corpus rather than an “Acrobat compatible” checkbox. [Poppler release notes](https://poppler.freedesktop.org/), [PdfPig text-order explanation](https://github.com/UglyToad/PdfPig).

### Inferences

- Build a fit/fidelity corpus covering scanned/image-only PDFs, large images, embedded and missing fonts, CJK, RTL and vertical/rotated text, ligatures, multicolumn reading order, crop boxes, page rotation, transparency/blend modes, color profiles, existing annotations, filled forms with incomplete appearances, password variants and malformed cross-reference tables. These are **test recommendations**, not assertions that any particular engine fails each class. [API settings that motivate tests](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [PDF.js font/asset settings](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html).
- Selection/search should initially use the renderer's own text geometry to avoid disagreement between a renderer and a second parser. Scans without an existing text layer need a separate OCR feature if searchable/selectable text is desired; no renderer-selection decision substitutes for that product requirement. [Text APIs](https://github.com/chromium/pdfium/blob/main/public/fpdf_text.h), [PdfPig extraction scope](https://github.com/UglyToad/PdfPig).
- Define read-only forms as “show current field appearances/values, no editing, submission, calculation promises or saving.” Explicitly exclude dynamic XFA and warn when unsupported. JavaScript-disabled viewers cannot promise Acrobat's scripted form calculations or open-action-driven presentation. [PDFium form actions](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h), [XFA build flags](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/05-configure.sh).
- For PDFium, let visible-page work preempt **queued** thumbnail/search/prefetch work. Split long jobs into small scheduled units and use progressive rendering where verified. A single global FIFO containing an entire document search can produce poor interaction even though work is off the UI thread. This scheduling recommendation follows the documented one-call-at-a-time limitation, not a measured wrapper defect. [Thread contract](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [progressive API](https://github.com/chromium/pdfium/blob/main/public/fpdf_progressive.h).

### Gaps

- Full engine support does not establish binding support. Need a small validation spike for text hit testing, copied text, search rectangles, destination navigation, form appearance/lifecycle, password retry and deterministic close on each shortlisted wrapper.
- No blanket thread-safety or bounded-cancellation guarantee was established for every Poppler frontend/version. Select a frontend, read its exact contract and serialize initial access conservatively; do not import PDFium's rules or assume per-document concurrency is safe.
- No universal fidelity promise, XFA compatibility promise, accessible-screen-reader UI implementation, signature-validation feature or DRM/security-handler coverage was established by this engine comparison.

## 3. What minimal F# architecture preserves speed, lifetime safety and security?

### Takeaway

Keep one small renderer adapter behind an F# reading-service boundary, with explicit ownership and a prioritized worker queue; use an engine-independent API only for actual viewer needs. For public use with untrusted PDFs, prefer a restartable, **OS-restricted** renderer helper, while measuring startup/IPC costs and recognizing that **a child process by itself is crash isolation, not a security sandbox**.

### Cited Findings

- Microsoft recommends `SafeHandle` for unmanaged-resource ownership, library-matching deallocation, correct native signatures/layouts and rooting callbacks for their entire native-use lifetime. A pointer to a managed delegate does not keep that delegate alive. [Official .NET native interop best practices](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices).
- PDFium memory-backed documents require their source buffer to stay valid until document close; custom document access requires its underlying file resources to remain valid. `FPDF_FORMFILLINFO` must remain valid until its form environment closes. Text search contexts have their own close operations. [Document memory/custom access](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [form callback lifetime](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h), [text/search lifetimes](https://github.com/chromium/pdfium/blob/main/public/fpdf_text.h).
- MuPDF's C API uses `fz_try`/`fz_catch` macros and `longjmp`-style error handling; official derived bindings translate to native-language exceptions. A naïve F# P/Invoke of arbitrary throwing MuPDF functions is therefore not an adequate error boundary: use a supported binding or a native shim that contains engine exceptions before returning to managed code. [C error handling](https://mupdf.readthedocs.io/en/latest/reference/c/overview.html), [derived bindings](https://mupdf.readthedocs.io/en/latest/reference/cxx-and-derived-bindings.html).
- Chromium's sandbox design explicitly relies on OS-enforced restrictions and least privilege, with a privileged broker mediating target access. Its process split is part of that design, not its entire security guarantee. PDFium's `FPDF_SetSandBoxPolicy` public header documents a machine-time-access policy; it does not claim to install Chromium's OS sandbox. [Chromium sandbox design](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md), [PDFium policy API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h).
- PDFium's typed actions include URI, remote-document and launch actions. Form callbacks can request URL navigation, local file access, upload/download and other host operations; document JavaScript/open/additional actions have explicit invocation APIs. These APIs make host action policy an application responsibility. [Document actions](https://github.com/chromium/pdfium/blob/main/public/fpdf_doc.h), [form/actions/callbacks](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h).
- PDF.js has an `enableScripting` viewer option whose generic viewer default is enabled in current source. It is distinct from needing JavaScript to run the PDF.js application itself. The loading API can fetch document URLs and auxiliary assets, making offline/local resource policy something to configure rather than assume. [Viewer options](https://github.com/mozilla/pdf.js/blob/master/web/app_options.js), [loading options](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html).

### Inferences

**Suggested components — a design recommendation, not implementation:**

1. **F# viewer state and UI:** document identity, navigation/zoom/rotation, visible pages, selection, find query/results and outline. Keep UI objects out of the native adapter. Start without an editor model, annotation-authoring model, persistence layer or plugin framework. Derive the adapter scope from the actual read APIs, not every native method. [PDFium read API surface](https://github.com/chromium/pdfium/tree/main/public).
2. **Small reading-service contract:** open with optional password and typed outcomes; document/page count, labels and dimensions; render a page/region at a requested transform; retrieve text geometry/copy text and bounded search results; links and outline; close. Return ordinary immutable records, owned bitmap buffers and typed internal/external destinations, not PDFium pointers or MuPDF structs. Add capability/error information only where needed (for example unsupported XFA). Avoid building a universal four-engine plugin API before one working engine. [Capabilities motivating the contract](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [text](https://github.com/chromium/pdfium/blob/main/public/fpdf_text.h), [navigation](https://github.com/chromium/pdfium/blob/main/public/fpdf_doc.h).
3. **Engine-owned scheduler:** with PDFium, one dedicated owner/dispatcher for **every call across the process**, including open, search, render, progressive continuation and disposal. Visible-page requests outrank prefetch, thumbnails and background search; bound the queue and coalesce obsolete zoom requests. Include document-generation/request IDs so stale results cannot paint into a newly opened document. Token cancellation can remove queued jobs and suppress stale results; it must not free buffers/pages/documents still used by native work. [Threading/lifetime contract](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [progressive contract](https://github.com/chromium/pdfium/blob/main/public/fpdf_progressive.h).
4. **Explicit ownership graph:** library runtime owns documents; documents keep streams/source buffers and form state alive; pages keep documents alive; text/search/render resources cannot outlive the relevant page/document. Use deterministic `IDisposable`/F# `use` internally, and SafeHandle-style ownership as a backstop, not the main scheduler. **A SafeHandle finalizer is not automatically PDFium-thread-safe:** any fallback release must obey the same global exclusion and keep parents/runtime alive; do not make finalizer-thread native calls race the dispatcher or destroy the library first. Follow the exact form-page close notification order documented by the selected API instead of guessing a universal ordering. [Microsoft guidance](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices), [PDFium global teardown](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [form lifecycle](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h).
5. **Pixel boundary, not UI-framework boundary:** return explicit width, height, stride, format/alpha semantics and an owned buffer or short-lived transferred surface. Validate dimension and byte-count arithmetic and cap render size/cache bytes. Copy/transfer before releasing native backing storage. Keep display transforms consistent for rendering, link hit testing and selection highlights; avoid routing a cross-platform core through Windows-only HDC/GDI concepts. [Bitmap formats, external-buffer ownership and transforms](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h).
6. **Startup path:** show UI, open only the document and currently needed page, render it promptly; defer whole-document text indexing, every page dimension, thumbnails and full outline expansion where possible. Prefer file/custom random access over unconditionally copying the entire PDF into managed memory, subject to correctness and benchmark results. A small measured page/bitmap LRU and adjacent-page prefetch are preferable to rendering everything. This is an architectural hypothesis to validate, not a claim that every engine opens lazily or every PDF supports equally cheap access. [PDFium file/memory/custom access API](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h).
7. **Native packaging/version boundary:** pin managed wrapper **and** native engine revision/build flavor together; record artifact hash/provenance, OS/RID/CPU, glibc versus musl requirements, renderer backend, V8/XFA flags and third-party notices. Use private application-controlled native resolution, not an arbitrary working-directory or user PATH lookup. Smoke-test installed/published artifacts on clean Windows/Linux machines, including Unicode paths, missing dependencies and wrong architecture. Audit security-update lag and rebuild/retest on upgrades; do not replace an old DLL with a random “latest” binary and presume ABI/export/behavior compatibility. [Generated matched bindings](https://github.com/Dtronix/PDFiumCore), [native platform matrix](https://github.com/bblanchon/pdfium-binaries), [authoritative header/signature guidance](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices).

**Isolation/security decision:**

- Treat PDF parsing, image/font decoding and rendering as an **untrusted-input native attack surface even in a read-only viewer**. Read-only application UX does not provide memory safety. A native crash in-process can terminate the UI; a helper permits containment/restart and an enforced timeout by terminating that helper. Neither stopping a Task nor disposing a document during an outstanding call is safe forced cancellation. [Malformed-input crash fixes in an actively maintained engine](https://poppler.freedesktop.org/), [cooperative cancellation contracts](https://github.com/ArtifexSoftware/mupdf/blob/master/include/mupdf/fitz/device.h).
- For a distributable reader, prefer one warm/reused renderer helper initially rather than launching one process per page. Give it only the chosen document/read-only handle or tightly brokered bytes, necessary read-only font/resources and bounded IPC; deny general filesystem writes, process creation and network access through actual OS policy. Validate IPC sizes/results as untrusted, enforce memory/CPU/job limits, and restart safely after faults. Windows restricted tokens/AppContainer-style facilities and Linux namespace/seccomp-style restrictions are possible mechanisms requiring platform-specific design/testing, **not protections obtained simply by `Process.Start`**. [OS-based sandbox rationale and broker model](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md).
- A helper has process/runtime/native initialization, IPC and pixel-transfer overhead. Keep the protocol small, reuse the worker, consider shared memory only after measurement, and measure cold and warm first-page latency against an in-process prototype. One worker serializes PDFium; separate processes can enable independent PDFium instances when justified, but a pool also multiplies memory and startup cost. No measured overhead figure is asserted here. [PDFium process-global resources](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [existing serialized .NET design](https://github.com/Dtronix/DtronixPdf).
- Disable **document JavaScript**, avoid automatic open/additional actions, omit launch/submit/import/attachment-execution behavior, and keep XFA out of the initial scope. For PDFium, prefer a verified non-V8 build and deny unsafe host callbacks. For PDF.js, keep JavaScript enabled for the viewer application while explicitly disabling **PDF scripting**. Disabled scripting also changes expected scripted form behavior; disclose that limitation. [Non-V8/XFA build](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/05-configure.sh), [form/action APIs](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h), [PDF.js scripting option](https://github.com/mozilla/pdf.js/blob/master/web/app_options.js).
- Internal page destinations can navigate inside the viewer. External links require an explicit user gesture, scheme allow-list and clear consent before handing off to a browser/application; never silently follow network, `file:`, custom-protocol, remote-document or launch actions. Do not open an arbitrary extracted string with the OS shell. Deny external network/launch actions by default; no consent-free background submission or downloads. [Action types](https://github.com/chromium/pdfium/blob/main/public/fpdf_doc.h), [network/file callbacks](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h).

**Proposed validation gate:**

- Compare shortlisted builds on the same clean Windows/Linux hardware and representative corpus: process launch-to-UI, open-to-first-visible-page, warm/cold file/cache conditions, page/zoom latency, selection/find responsiveness, peak resident memory, installed assets, close/reopen leaks, cancellation backlog and crash recovery. Separate native engine timing from UI, framework, worker-launch and file-I/O timing. Do not call a package “fast” solely because its README says so. [Engine APIs underlying comparable operations](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [MuPDF rendering/context model](https://mupdf.readthedocs.io/en/latest/reference/c/overview.html).
- Include malformed and oversized documents, malicious actions/URLs, font/image bombs, incorrect passwords, missing native assets and worker crashes. Check that resource limits, no-network policy and permission prompts remain enforced and that cancellation never races disposal. Include notices and exact native dependency versions in the release checklist. These are proposed acceptance tests, not completed security certification. [Sandbox principles](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md), [lifetime guidance](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices).
