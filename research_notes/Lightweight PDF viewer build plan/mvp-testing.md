# Lightweight PDF viewer: public test collections, coverage, and MVP gates

Research checked 2026-11-03. Scope: research and proposed product/test decisions only; no implementation and no corpus archives downloaded. Recommendations and numerical objectives below are proposals, **not measured performance claims about an engine**.

## 1. Which public collections are useful, available, and legally reusable?

### Takeaway

Start with a deliberately selected, pinned subset of Mozilla pdf.js and PDFium regression fixtures, plus the user's private real-world PDFs. Add veraPDF for atomic standards/structure cases and Ghent for difficult graphic-arts rendering; neither is a substitute for a general viewer corpus. Public download access does not by itself establish permission to redistribute every PDF.

### Inferences

**Recommended acquisition policy (proposal):**

1. Keep three layers: a small redistributable smoke set; an opt-in external regression cache fetched from pinned sources; and the user's **private** representative documents. Never commit personal PDFs, derived screenshots or extracted text to a public repository without explicit permission.
2. Start with approximately **60-100 distinct public files**, plus 20-40 diverse private files selected with the user. These are planning quantities, not claims about coverage. Favor small synthetic/reduced cases over bulk corpora. Add a minimized fixture for each real failure, only if permission allows.
3. Manifest each document: stable ID, category tags, source URL, pinned upstream commit, relative upstream path, SHA-256, byte/page counts, chosen pages, password source, expected load/result, extraction/search samples, known engine discrepancies, attribution/license evidence and `redistributable: yes/no/unknown`. Track why it exists; deduplicate by hash.
4. Unclear rights: keep URL/hash/instructions rather than bytes in a distributable test package, and require an explicit opt-in lawful fetch. Download instructions are not a substitute for checking source terms. Apply the same caution to rendered golden images and extracted text.
5. Prefer immutable commit links in the eventual acquisition manifest; branch links here are discovery pointers and can change. Avoid the assumption that a repository's software license automatically covers every embedded font, photograph, third-party document or externally linked publication.

### Gaps

- Isartor original distribution terms and original package documentation were not read: the authoritative landing page was blocked. No claim is made that the original Isartor package is CC BY merely because veraPDF's own corpus README says so.
- Poppler test-data binary inventory and file-specific permissions were not verified because its host required a browser challenge. MuPDF comprehensive public test-corpus availability was not established.
- Linked pdf.js downloads were not attempted; reachability, content hashes and rights must be checked for each selected file. No archive-size estimate for pdf.js/PDFium/veraPDF was established, and no bulk download is recommended.
- Ghent's archive-specific notices were not inspected; the public legal page is reason to be cautious, not a definitive interpretation of every packaged file's rights.

## 2. What coverage and automated acceptance strategy should the project use?

### Takeaway

Test end-to-end reading behavior, not just whether the native engine can produce a bitmap. Use explicit strata and expected outcomes, controlled same-engine visual baselines plus independent-engine spot checks, and separate ordinary-document performance goals from adversarial survival tests.

### Cited Findings

- pdf.js's manifest already separates equality/render cases from other tests and supplies page ranges, forms/annotation/password/print/XFA settings; it provides a practical model for a feature-aware case manifest. — [Manifest](https://raw.githubusercontent.com/mozilla/pdf.js/master/test/test_manifest.json)
- PDFium's instructions warn that platform font differences can cause pixel-test differences, and its external tests include backend/platform-specific expected PNGs. Pixel equality across arbitrary operating systems is consequently not an appropriate universal correctness oracle. — [PDFium README](https://github.com/chromium/pdfium/blob/main/README.md), [external expected images](https://pdfium.googlesource.com/pdfium_tests/+/refs/heads/main/pdfium/?format=JSON)
- veraPDF's corpus is intentionally atomic and clause-oriented for PDF/A, PDF/UA and PDF standards, whereas Ghent targets graphic-arts workflow behavior and settings. These cover different questions. — [veraPDF](https://github.com/veraPDF/veraPDF-corpus), [Ghent](https://gwg.org/resources/ghent-pdf-output-suite/)
- `mutool draw` exposes resolution, rotation, page boxes, ICC behavior, spot/overprint settings, text output, timings and memory controls. Those settings must be recorded for a reproducible differential comparison. — [MuPDF tool reference](https://mupdf.readthedocs.io/en/latest/tools/mutool-draw.html)
- PDFium exposes distinct errors for file access, malformed PDF, password, unsupported security and page failures; permissions are separately queryable. Test different UI outcomes rather than a single generic “cannot open” message. — [Public view API](https://raw.githubusercontent.com/chromium/pdfium/main/public/fpdfview.h)

### Inferences

**Proposed coverage strata and acceptance checks:**

| Stratum | Minimum selected examples / assertions |
|---|---|
| Ordinary small documents | One-page text, multipage office export, vector diagrams, thin rules, mixed orientation and page boxes; correct rendering, selection, page navigation and fit behavior. Include blank/zero-content pages. |
| Scans and OCR | Bilevel, gray and color scans; scan-only versus image plus invisible OCR text, rotated pages; no false “search broken” claim when there is no text layer, and selection aligns with visible content when OCR is present. OCR generation is not MVP. |
| Fonts and languages | Embedded/subset fonts, missing fonts, Type 1/TrueType/CFF/Type 3, ligatures, accents, missing/incorrect ToUnicode, Arabic/Hebrew RTL, mixed bidi, CJK horizontal/vertical. Assert glyph appearance **and separately** logical copy/search results and geometry. Missing or bad Unicode mapping is sometimes a document limitation; preserve as a known limitation, not a fabricated text oracle. |
| Images and color | JPEG, JPEG2000/JPX, JBIG2, CCITT, masks/soft masks, transparency groups and blend modes, gradients/patterns, RGB/gray/CMYK/ICCBased/Indexed/Separation/DeviceN, spot/overprint. Select focused pdf.js/PDFium cases and Ghent pages; record color-management/overprint policy instead of promising print-proof fidelity. |
| Scale | Long text books; hundreds/thousands of scanned pages; high byte count; one giant CAD/map page; mixed page dimensions; high DPI and extreme zoom. Page count, file size, decoded-image area and vector complexity are separate stress axes. Use tiles/bands/caps; never allocate a full giant-page bitmap at arbitrary zoom. |
| Navigation structures | Outlines, named/internal/external links, page labels (Roman/front matter), rotation/crop, destination zooms. Back/forward returns to the prior location; displayed page label and physical index are not conflated. |
| Encryption and permissions | Correct/wrong/missing password, retry/cancel, supported/unsupported security schemes and user permissions. Define product policy for copy/print restrictions and explain disabled actions; no password in logs or recent-file metadata. Do not present PDF permissions as a tamper-proof security boundary. |
| Annotations/forms/signatures | Existing annotation appearances and missing-appearance synthesis cases, flags controlling screen/print visibility, filled AcroForms, empty fields, signature-widget appearances; exercise a separate code path if the engine requires form overlays. Label unsupported dynamic/XFA behavior. Rendering a signature is not verification. |
| Malformed/hostile | Truncated xref, broken objects, cyclic/deep trees, huge coordinates, invalid filters/fonts/images, decompression expansion, extreme counts, embedded files, JavaScript, Launch/URI/submit actions. Assert bounded failure, no unintended file/network/process access, cancellable UI and worker recovery; never require all corrupt files to render. |
| Tagged/accessibility | Tagged and untagged documents, ActualText, headings/lists/tables, reading order, AltText, PDF/UA examples. Distinguish document structure extraction from screen-reader exposure. Test keyboard focus and named controls with Windows/Linux assistive technology; bitmap-only display is not document accessibility. |

**Proposed test layers:**

1. **Pure state/geometry tests:** F# unit/property tests for PDF-to-viewport coordinate transforms under crop/rotation/DPI, pointer-anchored zoom invariants, visible-page calculation, navigation history, cache eviction and stale-result rejection. Model the engine behind a small interface so scheduling can be tested with a slow/failing fake.
2. **Headless engine contract suite:** open, page count/size, render selected pages, extract text/character boxes, search, links/outlines, passwords, error classes, annotation/form display flags and deterministic disposal. Run the exact shipped native build on Windows and Linux. Report unsupported versus regression versus expected invalid.
3. **Visual regression:** store reviewed goldens for selected pages at fixed DPI/zoom/background/rotation and engine settings. Pin engine, font packages, color profiles and OS image; maintain platform baselines when justified. Compare thresholded pixel differences plus perceptual/structural similarity and produce overlays/diff thumbnails. Inspect changed regions manually; do not auto-bless engine upgrades. A small glyph/diacritic defect can matter even when whole-page similarity is high.
4. **Text/search tests:** explicit known strings and reading-order excerpts, whitespace/normalization policy, case/diacritic behavior, ligature search, line-end hyphenation policy, CJK/RTL, repeated hits, next/previous/wrap, exact highlight quads after zoom/rotation, copy spanning lines/pages. Track raw extracted text separately from normalized search text. OCR-free scans should return a clear no-text/no-hit result, not hang.
5. **UI automation:** launch/open via dialog, drag/drop and command line; open A then B while A is rendering; scroll rapidly, resize, zoom at pointer, switch fit mode, select/copy, navigate links/history/outline, search/cancel, wrong password/retry/cancel, failed page and worker crash. Test filename Unicode, spaces, long paths and unreadable/deleted/moved files. Check keyboard-only operation, DPI changes, X11/Wayland where shipped, and clipboard interoperation.
6. **Differential review:** compare a curated difficult subset with independently implemented engines: for example PDFium versus MuPDF and Poppler/pdf.js. More than one wrapper around PDFium is not an independent oracle. Disagreement triggers investigation against expected content/specification; majority vote is not proof.
7. **Stress/security:** subprocess timeouts and process-tree memory caps, repeated open/close, random page jumps, continuous scrolling, search plus rendering, low-memory eviction, malformed inputs and native engine upgrades. Native fuzz/sanitizer work belongs upstream or in a dedicated native harness; .NET exception handling alone cannot contain a native crash.
8. **Cadence (planning):** 10-20 tiny smoke documents per change; full selected corpus and both OSes nightly/release; optional large/private corpus locally or on controlled machines. Record corpus/engine/app versions with every result. Private tests must not leak screenshots/text into public CI artifacts.

**Proposed benchmark protocol and initial budgets:**

- Reference machine: document an actual older four-core x64 laptop/desktop, 8 GB RAM, local SSD, integrated GPU, 1920×1080 display, OS/build, power mode and scaling. Initially support Windows 11 x64 and one named current Linux LTS x64; ARM64 and broad distro support are separate matrices. Repeat at 200% scaling because pixel work increases. These are proposed conditions, not facts about user hardware.
- Measure timestamps separately: process creation; shell interactive; native library loaded; worker ready; document opened/page metadata ready; first **meaningful visible page pixels presented**; first crisp target-resolution page; text selection/search ready. A white window or spinner is not first page. For launch-open, start at process creation; for already-running open, start at user request. Do not silently compare these two timings.
- Separate process-cold/native-worker-cold with warm OS file cache; existing-process/reused-worker opens; and deliberately OS-cache-cold tests on a controlled test machine. Closing the app does **not** establish cold disk cache. Record caches, JIT/runtime startup, font/native-library initialization, antivirus and background load. Do not clear a user's OS caches during ordinary tests.
- Initial **targets** on that reference machine, for a curated ordinary set of ≤20 MB and ≤200 pages: p95 launch-to-first-meaningful-page ≤1.5 s; reused-process open-to-page ≤500 ms; shell input feedback ≤100 ms; cached zoom/scroll composition aim for 60 Hz, with p95 frame time ≤33 ms as an initial minimum. More complex docs get separate recorded budgets, not inclusion in a misleading universal bound. Measure at least 20 repetitions and report p50/p95, failures, sample size and variance.
- Search target: first useful hit ≤1 s for the ordinary set, then incremental results with cancellation; no forced full-document index before displaying page one. Record full-search duration separately. Cancellation acknowledgement target ≤100 ms; a native render may require cooperative pause support or eventual worker termination, not magically obey an F# cancellation token.
- Initial memory targets (total app **plus workers**, not only managed heap): idle working set ≤150 MB; ordinary reading steady-state ≤300 MB; normal raster cache ≤128 MiB; stress mode soft total budget 512 MiB before eviction/downsampling/backpressure. These are hypotheses to validate against UI framework/native engine overhead. Record peak private bytes/RSS, managed allocations, native cache and GPU resources where available; do not compare unlike Windows/Linux accounting as if identical.
- A 1024×1024 four-byte pixel tile is approximately 4 MiB before stride/extra copies; include decoded images, display lists, text caches, in-flight buffers, UI texture copies and multiple workers in memory accounting. Bound by bytes, not simply “ten pages.”
- Scheduler: visible page/tile first, neighboring prefetch second, search/thumbnail work last; cap concurrency and queues, deduplicate requests, key cache by document generation/page/scale/rotation/render options, cancel obsolete work, and never present results from a closed/replaced document. Start with one serialized engine owner per worker unless its actual API supports another safe pattern; do not assume all native handles are thread-safe.
- For hostile/complex jobs, use staged warning/timeout policies rather than declaring a fixed five-second kill correct for every valid CAD page. UI remains usable; user can cancel, lower quality or close; hard resource limit contains the worker. Process isolation is crash containment, **not automatically a security sandbox**: restrict file/network/process capabilities using an OS-specific design before calling it sandboxed.
- Baseline comparisons use the same PDFs, target page, visible resolution, cache state and timing definition. Record installed SumatraPDF on Windows and MuPDF/Okular on Linux, plus raw-engine diagnostics; never assert “engine X is fastest” from unrelated numbers. Product UI startup and bare raster time answer different questions.

### Gaps

- No application, native engine or hardware has been benchmarked here. Numerical objectives need calibration after a vertical slice; a package/working-set budget cannot be guaranteed from engine marketing.
- The user's actual document distribution, priority scripts, large-file sizes and printer needs are not yet known. Corpus strata should be weighted after inspecting their private manifest with permission.
- Full PDF/UA viewer accessibility, screen-reader reading order and reliable text recovery from broken encodings are not established by rendering or a validator run; they require their own capability and assistive-technology tests.

## 3. What should count as a useful MVP, and what comes next?

### Takeaway

Make the MVP an excellent **read-only reader**, not a bitmap demo or miniature editor. Keep F#/.NET for application state, scheduling and UI integration around a proven engine; explicitly defer editing, trustworthy signature verification, XFA and integrated printing until the reading path is stable.

### Cited Findings

- SumatraPDF documents ordinary reader expectations including continuous viewing, page/outline navigation, history, fit modes, zoom, text copy, find-next/previous and keyboard controls; it is a useful Windows behavior baseline rather than an MVP feature list to copy in full. — [Keyboard shortcuts](https://www.sumatrapdfreader.org/docs/Keyboard-shortcuts)
- Okular provides a useful Linux comparison for selection, content/thumbnails, annotations and actual digital-signature verification. Its broader capabilities are not evidence that these features are cheap to add to a new viewer. — [Official Okular site](https://okular.kde.org/)
- PDFium distinguishes no form, AcroForm, full XFA and XFA foreground forms; its build documentation says XFA requires JavaScript. A generic “supports forms” claim hides substantial differences. — [Form API](https://raw.githubusercontent.com/chromium/pdfium/main/public/fpdf_formfill.h), [build README](https://github.com/chromium/pdfium/blob/main/README.md)
- PDFium's signature API exposes signature data, byte ranges, subfilter, time and modification-permission information; such metadata access is distinct from establishing cryptographic validity and trust. — [Signature API](https://raw.githubusercontent.com/chromium/pdfium/main/public/fpdf_signature.h)
- Printing is platform-specific: Microsoft's WPF path centers on XPS and GDI, while CUPS accepts PDF and offers printer selection, media, fit, page ranges, duplex and job cancellation. Neither a common .NET language nor a render bitmap supplies a portable complete printing product. — [Microsoft printing overview](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview), [OpenPrinting CUPS](https://openprinting.github.io/cups/doc/options.html)
- MuPDF advertises its own AGPL/commercial code licensing and Okular GPLv2+; these matter for copying/embedding/distributing their code, not as a prohibition on treating installed applications as comparison tools. Test-document permissions remain a separate question. — [MuPDF README](https://raw.githubusercontent.com/ArtifexSoftware/mupdf/master/README), [Okular licensing statement](https://okular.kde.org/)

### Inferences

**Proposed essential MVP:**

- Open local PDFs via picker, drag/drop and command-line path. Show filename, current page/label and total pages; close/reopen safely. A single document/window is enough initially; tabs, cloud and document management are not required. Read-only must mean original bytes are never rewritten.
- Virtualized continuous vertical scrolling with mixed-sized pages, visible-page-first rendering, bounded caches and cancellation; quick next/previous/first/last/go-to-page. Outlines/bookmarks, internal links and back/forward navigation are essential for long manuals. Thumbnails may follow if outline/page navigation already works well.
- Fit width, fit page, percentage zoom, Ctrl+wheel anchored to the pointer, sensible resize behavior, horizontal panning and 90-degree view rotation. Retain a stable reading position while swapping low-resolution/old tiles for sharp ones; do not flash blank pages on every gesture.
- Text selection, Ctrl+C and context-menu copy; incremental document search with highlights, next/previous/wrap and clear no-text/no-hit status. No promise to OCR scans or reconstruct a perfect reading order from all malformed/unmapped fonts.
- Familiar keyboard operation: Ctrl+O, Ctrl+W, Ctrl+F, F3/Shift+F3, Ctrl+G, Page Up/Down, Home/End, +/-/fit commands, Escape to cancel/dismiss, Tab/Shift+Tab for controls and outline focus. Visible focus, accessible control names and usable high-DPI UI are essential, not optional polish.
- Handle password prompt/retry/cancel, unsupported encryption, unreadable/missing/corrupt files, per-page rendering errors, missing fonts/unsupported form types and engine-worker failure without crashing the shell. Keep diagnostic errors distinct and actionable; avoid exposing password/document contents in telemetry.
- External links: intentional user action only, show destination, allow only deliberately supported schemes and confirm handoff as appropriate. No PDF JavaScript, automatic launch/submit actions, hidden network fetches, executable attachments, multimedia or embedded browser in MVP.
- Existing annotations should **display** (including visible highlights, stamps, ink and note indicators/popups where supported); no annotation creation/move/delete/save. Test missing appearance streams and visibility flags, rather than assuming turning on one render flag covers everything.
- Existing AcroForm values and widgets should **display read-only**. Field input, tab/validation/calculation logic, appearance regeneration, fill/save and round-trip correctness are a later product. Dynamic XFA is explicitly unsupported in MVP; warn when detected rather than presenting a misleading blank page as success. Some static fallback appearance may display without implying XFA support.
- Existing signature **appearance** may display; label signatures “not verified” if detected. Do not use a green checkmark, imply signer identity/trust, or treat a visible handwritten image as a cryptographic signature. Verification later requires signed-byte-range checks, CMS/certificate chain/trust policy, timestamp/revocation behavior and modified-revision semantics; signing is another separate feature.
- Keyboard-accessible application UI is MVP. Full semantic document navigation for assistive technology must be separately scoped and tested; if not delivered, state the limitation. A tagged PDF plus image rendering is not an accessible-reader implementation.

**Explicit printing decision:** **integrated printing is next, not essential to this first read-only MVP.** This prioritizes fast, safe Windows/Linux reading over two native print stacks. Document the limitation clearly and offer an explicit “Open in another application for printing” handoff only when available; do not label that a complete Print implementation or invoke printing silently. This is a product tradeoff, not a claim that printing is unimportant. If the user's daily documents require printing, promote a **basic print milestone** to the release gate before they adopt it as their default viewer.

**Next print milestone proposal:** Windows native dialog/job integration through a chosen Windows bridge; Linux desktop print integration/CUPS, with packaging/portal behavior tested for the actual distribution. Provide printer, range/current/all pages, paper, fit/actual size, orientation, copies and duplex where supported; handle cancellation, unavailable printer/spooler and job failure. Preserve print annotation visibility semantics, protect passwords and temporary decrypted content, and do not rasterize every page at full printer DPI in memory. Prefer a supported vector/PDF submission path; when raster fallback is necessary, disclose quality limits and render in bounded bands. Booklet/poster, prepress separations, color-proof certification and advanced finishing are later. Source context: [Windows print models](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview), [CUPS options](https://openprinting.github.io/cups/doc/options.html).

**Suggested incremental plan / exit gates (not duration estimates):**

1. **Compatibility spike:** select 15-20 representative private/public cases covering basic text, scan, CJK/RTL, transparency, long/giant page, encryption and form/annotation display. Prove rendering **and** extraction/search/link/outline/password APIs on both target OSes. Confirm native package/build features and license requirements. Reject a convenient wrapper that exposes only page bitmaps if adding the rest is impractical.
2. **Vertical slice:** local open → isolated/background engine ownership → visible-page render → virtualized continuous UI → pointer zoom → selection/search/navigation. Begin measuring first page and peak memory immediately. Keep the F# domain/state/scheduler testable independently; interop and OS services sit behind narrow interfaces. This is an architecture proposal, not a claim that a particular toolkit solves it automatically.
3. **MVP hardening:** add error/password/recovery UX, safe external links, read-only annotation/forms appearances, keyboard/focus, DPI/platform packaging, permission policy and unsupported-feature messages. Pass selected goldens/text tests and all interaction flows on both OSes; demonstrate bounded memory and cancellation in long-scroll/search stress.
4. **Private beta:** run the user's private files, log only consented metadata, compare ordinary interactions with SumatraPDF/Okular/MuPDF, and turn failures into permission-cleared reduced fixtures. Review performance budgets from real measurements. Release only with no silent wrong-document/stale rendering, no unsupported forms passed off as complete, no original-file modifications, and no known blocker in the user's frequent files.
5. **After MVP:** basic integrated printing first if needed; then thumbnails/recent position/tabs, optional layers, better semantic accessibility, opt-in OCR. Treat annotation editing, AcroForm fill/save, signature verification/signing and XFA as separate investment decisions with new acceptance suites, not small checkboxes.

**Decision rule:** a mature reader may already solve the user's practical problem. Use SumatraPDF on Windows and MuPDF/Okular on Linux as baselines before spending months building parity. If building remains the goal, optimize the differentiator (fast familiar reading with predictable resources) instead of matching the competitors' entire feature surface. No competitor source copying is needed for behavior/performance comparisons; embedding or shipping engine/code introduces a separate license review.

### Gaps

- Printing priority is a deliberate proposed deferral pending confirmation from the user; it should not be silently removed from a general-purpose viewer promise.
- Toolkit choice, concrete .NET wrapper support, engine build options, process sandbox implementation and feature-specific API costs are adjacent architecture questions, not resolved by this test research.
- There is no asserted schedule, measured performance advantage, exhaustive security assurance or standards certification. Those require implementation evidence and broader review.
