# Build a Fast, Focused PDF Reader

**Start with F# on a supported .NET LTS release, Avalonia, and a validation spike around PDFium.** This best matches the requested Windows/Linux reach, strict application logic, and maintainable managed development without requiring Rust. Use a small XAML shell initially; consider Avalonia.FuncUI if keeping view composition in F# materially improves maintenance. Neither toolkit choice nor native rendering proves fast startup: no viewer was implemented or benchmarked in this research. Make the first release an uncluttered, read-only reader with selection, search, navigation, and faithful existing-content display—not merely a page-image demo. Defer integrated printing explicitly unless everyday printing makes it an adoption requirement, and validate native packaging, hostile-input containment, and representative documents before expanding scope.

## Avalonia fits the language preference; alternatives must earn their complexity

Avalonia supplies official F# templates, so FuncUI is optional. Prefer explicit views and a narrow binding model over reflection-heavy infrastructure. Compiled bindings can catch invalid property paths during builds; this complements, rather than replaces, an F# domain model. FuncUI supplies an F# view DSL and component/Elmish approaches, at the cost of another compatibility layer. Choose between them through a small maintenance/workflow trial, not an assumed performance difference. ([F# templates](https://github.com/AvaloniaUI/Avalonia.Templates), [compiled bindings](https://docs.avaloniaui.net/docs/data-binding/compiled-bindings), [FuncUI](https://github.com/fsprojects/Avalonia.FuncUI))

| GUI approach | Practical fit | Principal tradeoff |
|---|---|---|
| **Avalonia + F# XAML** | Recommended Windows/Linux starting point | Native dependencies, input, scaling, and compositor behavior still need testing. |
| Avalonia + FuncUI | Strong all-F# alternative | Additional view/update abstraction and upstream compatibility work. |
| GirCore/GTK4; GtkSharp/GTK3 | Consider for Linux-first integration | Bundle native GTK separately; GirCore's generated custom-subclass workflow is C#-oriented. GtkSharp is a different, GTK3 binding. |
| Qt Widgets/C++ + Qt PDF | Serious alternative if integrated reader components save enough effort | Changes language/toolchain and introduces module-specific license obligations. |
| Electron or a .NET-hosted webview | Useful when reusing PDF.js's viewer | Browser/runtime deployment and servicing; measure startup and process-tree memory. |
| WPF/WinUI; MAUI | Not the default for this brief | WPF/WinUI are Windows-specific; official MAUI platforms do not include Linux. |

Qt deserves particular attention because Qt PDF includes a viewer widget, search, bookmarks, and links, not just a raster API. GirCore documents separate native-library installation and C# source-generated subclassing; do not assume an entirely F# authoring workflow. Webviews are not automatically slow, but their runtime boundary needs justification; Tauri adds the Rust toolchain the user prefers to avoid. ([Qt PDF](https://doc.qt.io/qt-6.8/qtpdf-index.html), [GirCore](https://gircore.github.io/docs/get-started.html), [GtkSharp](https://github.com/GtkSharp/GtkSharp), [Electron architecture](https://www.electronjs.org/docs/latest/tutorial/process-model), [Tauri backends](https://v2.tauri.app/reference/webview-versions/), [WPF](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/), [MAUI platforms](https://learn.microsoft.com/en-us/dotnet/maui/supported-platforms))

Start with ordinary managed builds and self-contained folder releases. Compare ReadyToRun and NativeAOT only on the working viewer: AOT can remove JIT work but cannot eliminate document parsing, graphics initialization, or rasterization. It adds trimming/dependency restrictions and publishing work; single-file packaging is a separate decision with possible native extraction costs. Keep the edit/build loop ordinary even if releases eventually use AOT. Limit initial Linux support to named, tested glibc distributions; test X11 and Wayland-session behavior, including XWayland where used, rather than promising every distribution or backend. ([Publishing](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [NativeAOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [single-file behavior](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview), [Avalonia Linux](https://docs.avaloniaui.net/docs/platform-specific-guides/linux))

## Evaluate PDFium as an engine, not a ready-made reader

| Engine | Why consider it | Binding and licensing checkpoint |
|---|---|---|
| **PDFium** | Native C APIs for rendering, text, navigation, passwords, and forms | Evaluate PDFiumCore plus a small owned adapter; inspect actual native assets and exposed APIs. Preserve engine, wrapper, and dependency notices. |
| MuPDF | Rendering and structured-text capabilities; official generated C# bindings | AGPL or commercial engine license; verify binding packaging, native patch cadence, and independent wrapper terms. |
| Poppler | Established desktop rendering and document APIs | GPL, not LGPL; official frontend list does not establish a turnkey .NET viewer binding. |
| PDF.js | Existing browser viewer can save selection/search/UI implementation | Apache-2.0 project; requires a suitable web runtime and explicit document-scripting/resource policy. |

These are fit judgments, **not a speed ranking**. PDFiumCore documents native platform assets; DtronixPdf is worth evaluating for higher-level ownership/dispatch plumbing. README platform lists are not proof that a selected package publishes and runs correctly on both target systems. Inspect its native revision, architecture, build flags, exports, dependencies, and license files, then test the installed artifact. PdfPig is useful for extraction but is not a full page renderer. ([PDFium APIs](https://github.com/chromium/pdfium/tree/main/public), [PDFiumCore](https://github.com/Dtronix/PDFiumCore), [DtronixPdf](https://github.com/Dtronix/DtronixPdf), [MuPDF bindings](https://mupdf.readthedocs.io/en/latest/reference/cxx-and-derived-bindings.html), [Poppler](https://poppler.freedesktop.org/), [PDF.js](https://github.com/mozilla/pdf.js), [PdfPig](https://github.com/UglyToad/PdfPig))

**Licensing is artifact-specific, not legal advice.** PDFium's exact pinned license and third-party notices matter; a binary distributor's repository license does not replace them. MuPDF's commercial option does not automatically relicense an independently AGPL wrapper. Poppler explicitly states GPL obligations; a helper-process boundary is not a universal exemption. Qt's modules have differing terms, so neither “Qt always requires payment” nor “all Qt is LGPL” is sound. Review the intended distribution and complete dependency set before committing. ([PDFium license](https://github.com/chromium/pdfium/blob/main/LICENSE), [MuPDF licensing](https://mupdf.readthedocs.io/en/latest/license.html), [Poppler licensing](https://github.com/tsdgeos/poppler_mirror/blob/master/README.md), [Qt licensing](https://doc.qt.io/qt-6/licensing.html))

## Keep typed state separate from native ownership and security policy

Model document identity, viewport, navigation history, selection, search, and loading/error states as F# records and discriminated unions. A pure state transition produces explicit effects; an effect runner handles engine requests, clipboard, dialogs, and approved external navigation. Return immutable metadata, text geometry, typed destinations, and owned pixel buffers—not native handles—to the UI. Avoid designing a universal multi-engine plugin system before one engine works.

For PDFium, use **one prioritized engine-owner queue across the entire process**, including document opening, rendering, text/search, and disposal: upstream says none of its APIs are thread-safe. Visible-page work outranks queued search, thumbnails, and prefetch. Split background work into bounded units; coalesce obsolete zoom requests and attach document-generation IDs so late results cannot paint into a replacement document. Cancellation removes pending work and suppresses stale results; it does not interrupt arbitrary native calls. Progressive rendering offers cooperative pause points, not universal immediate cancellation. ([Thread/lifetime contract](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [progressive API](https://github.com/chromium/pdfium/blob/main/public/fpdf_progressive.h))

Own runtime → documents/source streams/form state → pages → text/search/render resources explicitly. Use deterministic disposal and SafeHandle-style backstops, keep callbacks and buffers alive, and preserve parent lifetimes. A finalizer must not call PDFium concurrently with the owner queue. Specify stride, pixel format, alpha semantics, and ownership at the bitmap boundary; check arithmetic and cap pixel/cache bytes. Pin wrapper and native engine together and resolve libraries from application-controlled locations. ([Interop guidance](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices), [PDFium ownership contracts](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h))

**Read-only is not a security boundary.** An in-process prototype is acceptable for controlled fixtures, not evidence of safe arbitrary-PDF handling. Prefer a reusable renderer helper for crash recovery and enforceable termination; a child process alone is not a sandbox. Before general untrusted-file distribution, implement and test OS restrictions on filesystem, network, process creation, and resources, with brokered read-only document access and validated bounded IPC. If sandboxing is deferred during private prototyping, disclose that limitation and restrict the deployment scope. Disable document JavaScript, automatic actions, launch/submission behavior, and XFA; confirm build flags and deny unsafe host callbacks. Allow external links only through deliberate user action, supported schemes, and visible handoff consent. ([Sandbox design](https://chromium.googlesource.com/chromium/src/+/main/docs/design/sandbox.md), [PDFium actions](https://github.com/chromium/pdfium/blob/main/public/fpdf_doc.h), [non-V8/XFA build configuration](https://github.com/bblanchon/pdfium-binaries/blob/master/steps/05-configure.sh))

## Make reading complete before adding editing or printing

The MVP should open local paths through picker, drag/drop, and command line; support one document per window; and never rewrite original bytes. Use one compact toolbar, no account/onboarding/network startup, and only user-requested search or outline panels. Provide virtualized continuous scrolling, mixed page sizes, page labels/go-to-page, fit width/page, percentage and pointer-anchored zoom, panning, rotation, outlines, internal links, and navigation history. Add selection/copy and incremental search with highlights, next/previous, cancellation, and clear no-text/no-hit feedback. Familiar shortcuts, visible keyboard focus, accessible control names, and high-DPI behavior belong in the first release. SumatraPDF offers a useful behavior baseline. ([Reader shortcuts](https://www.sumatrapdfreader.org/docs/Keyboard-shortcuts))

Display existing annotations and read-only AcroForm values, including widget overlays: PDFium's annotation render flag excludes widgets, which require a separate form draw path. Handle password retry/cancel, unsupported encryption, page failures, missing files, and worker recovery distinctly. Explicitly exclude dynamic XFA and scripted calculations. Signature appearance is not signature verification; scans without text require separate OCR. Keyboard-accessible controls also do not establish semantic document accessibility. ([Form rendering](https://github.com/chromium/pdfium/blob/main/public/fpdf_formfill.h), [render flags/errors](https://github.com/chromium/pdfium/blob/main/public/fpdfview.h), [signature API](https://github.com/chromium/pdfium/blob/main/public/fpdf_signature.h))

**Defer integrated printing from the first MVP**, clearly disclose it, and offer an explicit open-in-another-application handoff where available. If printing is routine for the user, promote basic printing to the adoption gate. It needs Windows and Linux integrations, printer/range/paper/scale/orientation/copies/duplex controls, cancellation/error handling, and bounded-memory output—not just a screenshot. Defer annotation editing, form fill/save, cryptographic verification/signing, OCR, tabs, multimedia, and advanced accessibility separately. ([Windows print models](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/documents/printing-overview), [CUPS options](https://openprinting.github.io/cups/doc/options.html))

## Build a rights-aware corpus, then require measured exit gates

Start with **60–100 selected public files plus 20–40 private examples**, planning quantities rather than coverage guarantees. Include office exports, scans with/without OCR, embedded/missing fonts, ligatures, CJK/RTL, transparency/color, cropped/rotated and giant pages, long documents, encryption, forms, annotations, malformed structure, and hostile actions. Keep private PDFs, screenshots, and extracted text out of public CI.

| Verified source | What is available and how to use it |
|---|---|
| [pdf.js PDFs](https://github.com/mozilla/pdf.js/tree/master/test/pdfs) and [manifest](https://github.com/mozilla/pdf.js/blob/master/test/test_manifest.json) | Committed binaries **and external `.pdf.link` references**. Manifest supplies checksums and test settings; not every file is in the checkout. External documents do not inherit the project's software license. |
| [PDFium resources](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/testing/resources/) | Actual PDFs plus `.in` templates requiring upstream generation. Good focused regression cases, not a representative reading library. |
| [Separate PDFium test repository](https://pdfium.googlesource.com/pdfium_tests/+/refs/heads/main/) | Additional PDFs and platform/backend-specific expected images; separately pinned through PDFium dependencies. Review third-party and file-specific rights. |
| [veraPDF corpus](https://github.com/veraPDF/veraPDF-corpus) | Actual atomic standards/conformance files; README declares CC BY 4.0. Check imported collections' notices; validation outcomes are not viewer scores. |
| [PDF Association PDF 2.0 examples](https://github.com/pdf-association/pdf20examples) | Small actual educational PDFs, CC BY-SA 4.0; useful smoke cases, explicitly not comprehensive. |
| [Ghent Output Suite](https://gwg.org/resources/ghent-pdf-output-suite/) | Downloadable assembled pages and patches stressing graphic-arts rendering. Settings matter; free download does not grant unrestricted reproduction. Check archive terms and [legal notice](https://gwg.org/terms-of-service/). |

Maintain a manifest with source/pinned revision/path, SHA-256, tags, selected pages, expected rendering/text outcomes, password handling, license evidence, and redistribution status. For uncertain rights, distribute references rather than bytes and require lawful opt-in acquisition. Recheck linked downloads and upstream checksums; deduplicate documents rather than counting test entries. Poppler has a separate test repository, but its current inventory/rights were not verified here; no comprehensive public MuPDF corpus was established. ([pdf.js downloader](https://github.com/mozilla/pdf.js/blob/master/test/downloadutils.mjs), [PDFium dependencies](https://github.com/chromium/pdfium/blob/main/DEPS), [Poppler test-data integration](https://github.com/tsdgeos/poppler_mirror/blob/master/.gitlab-ci.yml))

**First gate: compatibility.** Prove rendering, extraction/selection geometry, search, links/outlines, passwords, and annotation/form display on 15–20 discriminating cases on both OSes. Reject a bitmap-only wrapper if completing the reader is impractical. **Second gate: vertical slice.** Publish local open → background owner → visible page → scrolling/zoom → selection/search; instrument immediately. **Third gate: hardening.** Add failure/security policy, resource bounds, keyboard/DPI/platform integration, and installed-package tests. **Fourth gate: private beta.** Exercise frequent real documents, compare installed SumatraPDF and MuPDF/Okular, and reduce failures into permission-cleared fixtures.

Use pure state/geometry tests, exact-shipped-engine contract tests, reviewed visual goldens, text/search assertions, interaction automation, and hostile-input recovery tests. Pin fonts/render settings and allow justified platform baselines; PDFium warns font differences affect pixel tests. Independently compare difficult cases with MuPDF or another engine; disagreement requires investigation, not majority voting. ([PDFium testing guidance](https://github.com/chromium/pdfium/blob/main/README.md), [MuPDF diagnostic rendering](https://mupdf.readthedocs.io/en/latest/tools/mutool-draw.html))

**Indicative acceptance targets—not promises:** on a documented older four-core, 8-GB, SSD reference machine, target p95 launch-to-meaningful-page ≤1.5 seconds and reused-process open ≤500 ms for a curated ordinary set ≤20 MB/200 pages; input feedback ≤100 ms, first useful search hit ≤1 second, and ordinary total process-tree memory ≤300 MB with a ≤128-MiB raster cache. Calibrate after the slice; complex/hostile documents need separate budgets. Run at least 20 repetitions, reporting p50/p95, failures, cache conditions, shell/page/crisp-render milestones, and peak memory. Distinguish fresh-process/warm-cache from genuinely OS-cache-cold runs. Measure installed bytes and incremental/clean/publish build times separately; never hide a background prewarmed instance.

## Conclusion

The critical decision is whether the chosen stack delivers predictable reading on the user's actual documents within an explicit support boundary. If native binding gaps, sandboxing, or fidelity dominate the work, change that boundary before multiplying features or engines. An existing lightweight reader remains a legitimate outcome if the prototype cannot justify its ongoing security and compatibility maintenance.
